# 그래프와 상세 설명으로 인계하기

QNA·USER_INTENT·SPEC·CHECKLIST와 현재 코드·실행 근거를 읽고 [HANDOFF 양식](../assets/HANDOFF.md)을 실제 내용으로 작성한다. 사용자가 방법의 이유와 전체 동작, 실패와 한계를 자기 프로젝트에 연결해 이해할 수 있도록 설명한다.

## 구성

먼저 해결한 문제, 실제 완성 범위, 중요한 선택, 확인한 결과와 남은 일을 연결된 문단으로 요약한다. 이후 필요한 작은 그림과 인접 상세 설명을 배치한다. 작업 현황 그래프는 작업 ID·선행·병렬·통합·현재 상태를 나타내고, 제품 동작 그림은 실제 데이터와 상태의 흐름을 나타낸다.

다음 여섯 관점을 모두 검토한다. 단순한 경우 그림을 합치고, 적용되지 않는 관점은 이유를 표시한다.

| 관점 | 그림·설명에 담을 내용 | 답할 수 있어야 하는 질문 |
|---|---|---|
| 선택과 절충 | 목표·제약, 실제 대안, 선택 이유·포기한 이점, 판단 주체 | 왜 이 방법이며 언제 다른 방법이 나은가? |
| 요청·데이터 흐름 | 실제 역할·화면/CLI/API·컴포넌트, 주요 값·ID/버전·상태 소유자, 계산·검증·저장·조회 | 한 요청이 어디를 거쳐 어떤 상태로 끝나는가? |
| 검증의 신뢰 경계 | 기준 원본·규칙, 검증 전 출력, 독립 계산과 통과/거부 경로 | 무엇을 믿지 않고 무엇으로 검사하며 유효성과 최적성이 어떻게 다른가? |
| 실패·변경 | 실행 한도·오류·지연·취소·원본 변경의 실제 조건과 분기 | 결과·사용자 표시·기존 저장 상태가 각각 어떻게 되는가? |
| 품질·한계 | 실제 비교·작은 정답·조건 변화 실험과 관측값, 주장 범위·미확인·다음 검증 | AI 설명 밖에 어떤 근거가 있고 조건이 바뀌면 무엇을 다시 확인하는가? |
| 실제 AI 협업 | 발견자·방법→재현/제안→수용·수정·기각 판단→코드 변경→재검사 | 누가 무엇을 왜 바꿨고 무엇을 그대로 받아들였는가? |

품질 비교에는 같은 입력·제약·자원 조건과 원래 단위의 수치를 둔다. 증거가 없는 최적성·성능 주장은 미확인으로 적는다. 없는 진행률·기능·가짜 실패나 기각 이력을 그림을 채우기 위해 추가하지 않는다.

중요한 업무 규칙이나 데이터 기준이 바뀔 때 함께 검토할 명세·입력 조건·계산·검증·기대값·설명과 재검사 범위를 기존 그림·인접 설명에 연결한다. 예상 변경 영향은 실제 구현·실험 결과와 구분한다.

## 그래프를 읽을 수 있게 만들기

Markdown에는 Mermaid 흐름도·시퀀스도·상태도를 우선 사용한다. 그림마다 제목, 한 문장 의미, 화살표 범례를 둔다. 참조할 노드 ID는 렌더링 라벨에도 표시한다. 데이터 전달·상태 전이·판단 근거를 구별하고 조건부 실패의 선에는 발동 조건과 정상 경로를 표시한다.

긴 경로는 정상·예외 또는 생성·조회처럼 의미 단위로 나눈다. 긴 라벨은 짧게 쓰고 단어 중간에서 끊기지 않게 줄을 나눈다. 가능한 렌더러로 글자·선 교차·크기를 확인한다. 렌더러가 없으면 텍스트 흐름·표를 함께 제공하고 시각 확인의 한계를 남긴다.

각 그림 옆에서 **노드/연결 → 의미·전달 값/조건 → 실제 코드 → 실행 근거·관측값 → 한계**를 연결한다. 같은 경로의 근거는 표 한 행이나 문단으로 묶는다. 그림과 인접 설명만으로 핵심 동작이 이해되고 상세 로그·검사 목록은 근거 위치에 연결한다.

정상 요청 하나와 실제 적용되는 중요한 실패·변경 경로를 입력부터 결과·사용자 표시·저장 상태까지 실제 노드로 따라 설명한다. 해당 실패·변경 경로가 없으면 그 사실과 이유를 적는다. 실행된 기능과 설계·미구현, 실제 관측과 정적 코드 판단을 구분한다.

## 독립 읽기와 사실 대조

1. 작성에 참여하지 않은 새 맥락의 독자에게 그림·인접 범례·표·요약과 프로젝트에 맞춘 여섯 관점 질문을 제공한다. 독자가 자기 말로 답하고 정상 경로와 적용되는 실패·변경 경로를 추적해 보고서의 **첫 읽기** 구획을 저장한다. 코드·부모 해설·채운 체크리스트는 이 단계에서 제외한다.
2. 첫 읽기에서 핵심 경로·판단을 설명하기 어려우면 후속 자료를 열기 전에 혼동 지점을 반환한다. 메인이 설명을 보완하면 같은 독자가 자료 공개 전에 다시 읽는다. 이해 가능한 상태가 되면 원자료·현재 의도·SPEC·코드·검사·CHECKLIST를 읽고 같은 보고서의 **사실 대조** 구획에 첫 답변·노드별 일치·차이·미확인과 실제 근거·주장 범위를 연결한다. 현재 구현의 중요한 분기가 그림에 빠졌는지도 대조한다. 변하지 않은 설명은 첫 구획을 참조한다. [순차 검토 절차](checks-and-review.md)에 따라 한 배정에서 이어갈 수 있다. 메인은 실제 읽기·저장 순서와 첫 구획 보존을 확인한다.
3. 메인은 지적을 실제 확인해 처리하고 영향받은 연결만 재확인한다. 코드 공개 뒤 의미·경로 설명을 수정했다면 해당 부분은 새로운 독자가 처음 읽도록 한다. 의미가 같은 오탈자·줄바꿈·선 배치는 기존 검토자가 시각 확인할 수 있다.

적용 관점에 구체적인 답과 근거가 있고 중요한 사실 오류 없이 핵심 경로를 추적할 수 있을 때 읽기·대조 결과를 기록한다. CHECKLIST에 보고 위치, 지적 처분, 렌더링 상태와 남은 한계를 연결한다. 제품 검사 결과와 그래프 검토 결과는 각각 실제 범위로 표현한다.

## 사용자에게 설명하고 이어가기

검토한 그림으로 핵심 선택과 경로·실패 분기를 설명하고, 실제 재현 순서와 관찰할 결과를 전달한다. 사용자가 결과를 직접 설명·운영하거나 후속 질문에 답할 준비가 필요하면 해당 노드와 조건 변화에 대한 짧은 이해 QNA로 이어간다. 사용자가 요청하거나 실제 오해가 드러난 경우에도 적용한다. 답변에서 오해가 나타나면 그림·설명을 먼저 보완한다. 사용자가 실제로 설명한 범위만 이해 확인으로 기록한다.

완성한 자료는 이해 답변 대기와 관계없이 전달한다. 미완료 필수 항목의 영향, 확인하지 않은 조건과 다음 재개 지점을 적고 체크리스트의 다음 행동으로 연결한다.
