# 명세·실행·에이전트 운영

## 명세와 계획

확인한 요구를 SPEC의 역할별 동작·입출력·단위/ID/버전·상태 소유자·통과 조건으로 작성한다. 정상 흐름과 중요한 실패·한도·원본 변경 시 결과 처리, 사용자 표시, 저장 상태를 정의한다. 실제 프로젝트에 필요한 구성요소를 선택한다.

중요한 방법에는 목표·제약·실제 대안·선택 이유·포기한 이점·주장 범위를 연결한다. 실행 계획은 CHECKLIST의 작업표 한 곳에 작업 ID, 선행 관계, 산출물, 수정 소유권, 완료 검사와 통합 순서를 둔다. SPEC의 요구·검사 계획은 이 작업 ID에 연결한다. 사용자 제공 시간·자원 안에서 핵심 구현·검증·설명 시간을 함께 배분한다. 독립 요구 검토의 중요한 지적을 해결한 범위부터 구현한다.

## 역할과 배정

메인이 QNA·의도·SPEC·CHECKLIST·HANDOFF를 관리한다. 하위 에이전트는 지정된 코드 또는 고유 보고서를 작성한다. 실제 가용 도구·동시 실행 여유를 확인하고 독립 작업을 병렬 배정한다.

| 역할 | 입력·작업 | 필요한 독립성 |
|---|---|---|
| 초기 조사 | 현재 원자료·질문/답변·존재하는 의도에서 분석·질문안·검사 기준 도출 | 서로 다른 자료·관점을 병행. 아직 없는 명세를 기다리지 않음 |
| 구현 전 요구 검토 | 원자료에서 첫 요구 목록을 만든 뒤 명세·계획과 대조 | 부모 맥락을 상속하지 않는 새 에이전트 |
| 구현 | 확정된 명세·작업·인터페이스와 소유 경로 | 수정 경로가 겹치지 않는 모듈을 병행 |
| 실행·최종 검토 | 원문에 따른 기대와 실제 실행 결과·최종 요구 충족 대조 | 아래 조건을 충족하는 최초 요구 검토자 또는 새 맥락 비작성자 |
| 그래프 독자 | 그림과 인접 설명을 먼저 읽고 이후 코드·근거 대조 | 작성에 참여하지 않은 새 맥락 |

새 맥락 생성 기능이 있으면 해당 옵션을 사용한다. 예를 들어 `spawn_agent`에서는 `fork_turns="none"`을 지정한다. 같은 대화를 상속한 에이전트에게 역할명만 바꿔 독립성을 부여할 수는 없다. 도구가 제공되지 않는 경우 가능한 자체 검사는 수행하고 독립 검토의 미완료와 영향을 기록한다.

배정은 **작업 목적·관련 ID/기준, 읽을 자료와 순서, 선행 계약·수정 경로, 완료 검사·중단 조건, 보고 위치**로 정리한다. 같은 계약은 실제 위치를 연결하고 변경점만 전달한다. 일반 에이전트는 존재하는 관련 의도를 읽고 제품 구현부터 해당 SPEC을 기준으로 작업한다. 원문 우선 검토와 그래프 첫 읽기는 제한된 입력 순서를 따른다.

반환은 변경 파일, 적용한 기준, 실제 명령/입력/결과, 가정·결함·미확인을 포함한다. 메인은 실제 변경과 근거·통합 동작을 확인해 CHECKLIST에 반영한다. 에이전트 간 이견은 원자료·사용자 목적·실제 관측으로 판단하고, 업무 의미가 달라지는 선택은 QNA로 확인한다.

## 구현과 검사

가장 작은 전체 흐름을 입력→처리→검증→출력/저장→조회까지 연결해 실행한 뒤 필요한 범위를 확장한다. 웹은 실제 화면, CLI는 명령·파일, API는 요청·응답으로 확인한다. 통합한 기능과 남은 위험을 사용자에게 설명한다.

- **필수 동작·실패:** 정상 입력과 중요한 경계·누락·권한·시간/크기 한도·오류를 검사한다. 부분 결과·빈 결과·실패, 계산 완료·검증 완료·저장 완료를 실제 상태에 맞춰 구분한다.
- **데이터 변경·비동기:** 적용되는 경우 원본 버전 변경·늦은 응답·취소를 주입해 현재 요청에 다른 결과가 덮이지 않는지 확인한다. 진행 표시에는 실제 산정 기준을 사용한다.
- **출력 검증:** 생성기의 성공 플래그·합계·점수 대신 기준 원본과 규칙에서 ID·중복·누락·제약·합계를 다시 판단한다. 조작된 출력도 직접 넣어 거부 또는 재계산을 확인한다. 계산 문제가 아니면 독립적으로 도출한 기대 동작과 비교한다.
- **품질 근거:** 품질 차이가 중요한 작업에서는 동일 조건의 기준 방법, 손으로 검산하거나 독립 열거할 수 있는 작은 정답, 주요 조건 변화 중 필요한 실험을 수행한다. 입력·종료 조건·seed 등 재현 정보를 남긴다. 서로 다른 가중치의 총점은 같은 지표로 비교하지 않는다.

유효성, 관측한 품질, 최적성·정확성의 증명 범위를 따로 설명한다. 작은 사례의 일치, 알고리즘 원리, 코드 정확성, 특정 실행의 종료 상태를 근거에 맞게 구분한다. 실제 실행하지 않은 비교나 실패·개선 이력을 만들지 않는다.

검사 기록에는 요구/작업 ID, 입력·코드 기준, 명령 또는 화면 동작, 실제 결과, 판정과 한계를 남긴다. 중요한 결함은 동일 입력의 실패→원인→수정→같은 실패와 관련 정상 검사로 연결한다. 새 변경이나 남은 우려가 없다면 통과한 검사를 반복하지 않고 다음 작업으로 진행한다.

최초 요구 검토자가 제품 코드·최종 설명 작성에 참여하지 않고 첫 독립 판단과 현재 기준을 추적할 수 있으면 최종 실제 검사·요구 대조까지 맡긴다. 최종에는 **현재 원문 전체의 필수 조건 → 실제 결과·검사 근거**를 대조해 첫 목록의 누락도 확인한다. 작성자 테스트의 기대값·성공 표시를 정답으로 삼지 않고 직접 실행한다. 변경 원문은 부모 해석보다 먼저 읽어 추가 판단을 보존한다.

최초 입력 오염·작성 참여·기준 추적 불가, 목적·권한·우선순위·핵심 계약의 큰 변경, 반복되는 요구 오해나 설명되지 않은 중대한 결함에는 해당 범위를 새 맥락 검토자에게 맡긴다. 검토자 재사용에는 초기 사각지대가 이어질 수 있다는 한계가 있다. 최종 그래프는 별도의 새 독자가 읽는다.

## 변경과 재개

CHECKLIST의 현재 목적·질문·기준과 실제 파일 변경을 읽고 재개한다. 에이전트 ID는 실제 생존 상태를 확인한다. 새 답변이 기준을 바꾸면 영향 작업을 먼저 멈추거나 반환을 보류시킨다. [질문·의도 절차](qna-and-intent.md)로 답변을 접수하고 현재 의도·명세·CHECKLIST의 영향 기준과 다음 행동을 기록한 뒤 코드 변경이나 하위 작업을 재개한다. 재배정에는 갱신한 소유권과 기준을 전달하고, 중단을 확인할 수 없는 경로에는 새 동시 쓰기를 배정하지 않는다.

이전 기준의 늦은 결과는 현재 의도·명세에 다시 대조해 유효한 부분만 통합한다. 문제 해결 뒤에는 체크리스트의 다음 행동을 실행해 본래 목적을 이어간다. 변경된 기준·파일과 영향 요구를 기준으로 재검사와 재사용할 근거를 정하고 관련 그래프를 갱신한다. 영향이 불명확하면 넓게 확인한다. 짧은 전체 검사는 복잡한 선별 절차 없이 실행해도 된다.
