# 함께 파악하고 명세·계획으로 연결하기

시작할 때 읽고 G0~G6에 적용한다. 메인 orchestrator가 원문 이해, 질문 정리, 의도 반영, 명세·계획, 위임·통합, 검증·설명을 책임진다. 하위 에이전트 보고는 메인이 확인할 입력이며 사용자에게 그대로 전달하는 최종 판정이 아니다.

## 1. 네 단계의 연결

| 사용자에게 보이는 단계 | orchestrator가 정리할 내용 | 다음 단계로 넘길 기준 |
|---|---|---|
| ① 프로젝트 파악 | 대상 사용자, 현재 업무, 원하는 변화, 필수 흐름, 원자료의 범위, 아직 모르는 점 | 실제 읽은 출처가 있고 사실·해석·불확실성이 구분됨 |
| ② 확인 | 사용자·현업 담당자별 질문, 답변에 담긴 목적과 이유, 우선순위·절충, 대기 작업 | 관련 범위의 중요한 불확실성이 해소되거나 명시적으로 위임됨 |
| ③ 명세·계획 | 무엇을 어떻게 만들고 어떤 검사로 완료를 판정할지, 순서·역할·의존성 | 원자료·답변과 연결한 명세·계획 및 독립 대조, 중요한 차이 해결 |
| ④ 구현·테스트 | 명세에 따른 구현, 실제 검사, 독립 피드백, 수정·재검사 | 필수 흐름과 조건에 최신 실행 근거가 있고 남은 한계가 명확함 |

각 단계는 전체를 한 번씩 끝내는 경직된 절차가 아니다. 새로운 질문이 나오면 영향받는 결정만 ②로, 설계가 바뀌면 관련 명세·계획만 ③으로 되돌린다. 이미 준비된 범위의 작업은 계속한다. 다만 불명확한 요구를 임의로 정한 채 제품을 먼저 완성하고 나중에 명세를 맞추지 않는다.

## 2. 진행 설명과 질문을 분리한다

실질적인 답변은 QNA에서 받는다. **진행 설명까지 문서 안에만 가두지 않는다.** 메인은 다음 내용을 짧은 채팅으로 알려 사용자가 현재 판단과 다음 행동을 이해하게 한다.

- 지금 어느 단계·핵심 흐름을 다루는지.
- 새로 확인한 사실이나 선택 이유가 사용자 목적에 어떤 의미인지.
- 실제 확인한 동작, 아직 검증하지 않은 부분, 독립 검토의 중요한 지적과 처리.
- 다음 행동, 사용자의 답이 필요한 QNA ID와 그 답을 기다리는 작업.

단계 시작·전환, 중요한 발견·계획 변경, 핵심 흐름 통합, 검토 지적 처리 때 설명한다. 장시간 작업에서는 약 1분을 넘기지 않도록 간결한 진행 설명을 제공한다. 같은 문구를 반복하거나 상세 도구 출력을 나열하지 않는다. 사용자에게 진행 설명을 했다는 사실을 승인으로 해석하지 않는다. 기존의 명확한 답변·위임 범위 안에서는 그대로 진행한다.

## 3. 현업 질문도 확인 과정에 포함한다

질문마다 **대상 / 원문에서 모르는 점 / 가능한 해석과 영향 / 답변 출처 / 반영할 요구**를 QNA에 둔다. 현업 질문은 현재 업무의 병목, 성공·실패 사례, 반드시 지켜야 할 조건처럼 구현 판단을 바꾸는 것에 집중한다. 유도 질문으로 원하는 답을 끌어내지 않는다.

허용된 질의 채널이 있으면 그 범위에서 질문하고 원문 응답을 기록한다. 사용자에게 전달을 맡겨야 하면 그대로 보낼 질문과 답변 칸을 문서에 둔다. 응답이 없으면 `미응답`으로 남긴다. AI의 예상 답이나 가상 담당자를 실제 현업 답변으로 기록하지 않는다. 받은 답의 권위·적용 범위와 사용자 목적의 충돌을 확인한 뒤 QNA→USER_INTENT→REQUIREMENTS에 연결한다.

## 4. 구현 기준인 SPEC을 만든다

G2에서 [SPEC 양식](../assets/SPEC.md)을 채운다. **한 문서에 명세와 실행 계획을 구분**한다. 기존 명세·계획이 있으면 해당 절을 WORKLOG에 매핑해 사용하며 사본을 늘리지 않는다. 원문 인용과 전체 추적표는 REQUIREMENTS, 실제 질문·답은 QNA, 실행 상태·로그는 WORKLOG에 두고 SPEC에서는 ID로 연결한다.

명세에는 다음을 실제 프로젝트에 맞게 담는다.

- 목적·성공 기준·대상 역할, 구현 범위·범위 밖, 확인한 요구와 미확정 가정.
- 역할별 `입력/사건 → 정상 동작 → 금지 결과·예외 → 관찰 가능한 통과 조건`.
- 필요한 데이터 형식·단위·ID·버전, 인터페이스 계약, 상태 소유자, 검증·저장 경계. 없는 DB·API·큐를 요구하지 않는다.
- 중요한 방법 선택과 대안·절충, 실행 한도·실패·데이터 변경 처리, 보장하는 범위와 한계.
- 테스트 입력·기대 결과·확인 방법. 기대 결과는 구현 자체가 아닌 원자료와 규칙에서 도출한다.

실행 계획에는 작업 ID, 연결 명세·요구, 선행 작업, 담당과 파일 소유권, 완료 검사, 통합 순서와 검토 시점을 둔다. 구현뿐 아니라 통합·독립 검증·결함 수정·그래프 설명에 필요한 여유를 포함한다. 계획은 사용자 제공 일정·자원에 맞추며 임의의 제한 시간을 만들지 않는다. 실제 진행 상태는 WORKLOG에서 같은 작업 ID로 관리한다.

## 5. 기준을 확정하고 구현에 전달한다

새 맥락 감사자는 원자료에서 요구사항을 먼저 독립적으로 도출한 뒤 SPEC·계획을 대조한다. 원문 기반 요구 목록은 [독립 감사 절차](requirements-and-audit.md)를 따른다. 명세의 누락·모순, 사용자 의도와 다른 우선순위, 판정 불가능한 통과 조건, 계획의 빠진 검사·의존성을 확인한다.

메인은 중요한 차이를 해결하고 **SPEC 버전, 의도 버전, 근거 답변, 구현을 시작할 범위, 보류 범위**를 남긴다. 사용자에게 명세·계획 링크와 핵심 선택·실행 순서·검증 방식을 설명한다. 이미 정해진 사항을 다시 승인받지는 않는다. 사용자의 선택이 실제 필요한 미확정 사항만 QNA로 묻는다.

해당 작업을 배정하려면 연결 명세·요구·통과 조건이 있고, 영향을 주는 질문과 독립 검토 지적이 해결되어야 한다. 조사·실험용 프로토타입은 별도로 표시하고 제품 구현 완료로 계산하지 않는다. 하위 에이전트에게 SPEC 버전·절·작업 ID를 전달하고 반환 시 어떤 기준으로 확인했는지 받는다.

## 6. 변경을 숨기지 않는다

답변·원자료·실행 결과가 기준을 바꾸면 관련 SPEC 절과 계획 작업을 먼저 재검토한다. 업무 의미가 바뀌면 QNA로 확인하고, 위임된 구현 수정이면 근거를 기록한다. 바뀐 범위·이유·검증 영향을 사용자에게 설명하고 에이전트에 새 버전을 전달한다. 기존에 통과한 검사를 변경된 기준의 증거로 재사용하지 않는다. 실제 제품과 계획의 차이는 최종 HANDOFF에도 반영한다.
