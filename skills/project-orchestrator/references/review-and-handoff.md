# 설계 설명과 인수인계

G6에서 읽는다. 사용자가 설계 선택·동작 원리·검증 근거·한계를 이해하고, 다른 담당자와 검토하거나 후속 작업을 이어갈 수 있도록 정리한다. 문서 작성, 구현·검증 완료, 사용자의 이해 확인은 각각 실제 근거로 구분한다.

## 1. 최신 근거부터 모은다

USER_INTENT, QNA의 실제 답변, REQUIREMENTS의 현재 추적표, SPEC 명세·계획, WORKLOG의 결정·흐름도·실행·협업 기록, 마지막 변경 이후의 검사 결과를 읽는다. 독립 최종 검토의 미해결 항목도 포함한다.

주장마다 출처를 구분한다.

- **사용자 직접 판단:** 실제 답변과 연결된 목적·선택·이유. 원문에 없는 의도를 덧붙이지 않는다.
- **에이전트 판단:** 위임된 구현 선택, 비교 결과의 해석, 추천. 사용자가 직접 내린 판단으로 쓰지 않는다.
- **관측 결과:** 누가 어떤 입력과 명령/화면 동작으로 확인했는지. 보고만 받은 내용과 직접 재확인한 내용을 구분한다.
- **미확인:** 미실행, 가정, 최적성 근거 부족, 이해 확인 답변 대기. 완료 표현으로 바꾸지 않는다.

코드·문서·실행 기록이 충돌하면 최신 사실을 확인하고 고친다. 시간이 없어 해결하지 못하면 충돌과 영향을 적는다. 검증 실패를 문장 표현으로 덮지 않는다.

## 2. HANDOFF를 두 층으로 쓴다

[HANDOFF 양식](../assets/HANDOFF.md)을 실제 내용으로 채운다. 빈 틀을 전달하지 않는다. 적용되지 않는 항목은 이유를 짧게 쓰고, 중복 설명은 링크로 합친다. 각 층에 [그래프 절차](graph-handoff.md)의 그림과 인접 근거를 배치하고, 작성 후 새 맥락 독자의 읽기 검토와 사실 대조를 수행한다.

### 첫 층: 연결된 핵심 요약

저장소를 모르는 독자도 이해할 수 있도록 몇 문단으로 이어 쓴다. 한 줄짜리 키워드 목록으로 끝내지 않는다.

1. 누구의 어떤 문제를 해결하며 실제로 완성한 범위가 무엇인지 설명한다.
2. 중요한 선택과 대안, 사용자가 정한 우선순위, 에이전트가 판단한 절충을 연결한다.
3. 입력이 결과가 되는 흐름과 핵심 검증 위치를 코드와 함께 설명한다.
4. 실제 관측 결과가 무엇을 뒷받침하며 무엇까지 보장하지 않는지 설명한다.
5. 남은 제한, 실패·변경 시 동작, 다음에 확인할 중요한 사항을 적는다.

목업, 실제 구현, 검증된 동작을 구분한다. “테스트 통과” 대신 핵심 검사가 확인한 사실과 범위를 설명한다. 기술 이름은 사용자에게 생기는 차이와 함께 쓴다.

### 둘째 층: 설계 검토와 유지보수 관점

아래 관점으로 프로젝트를 설명한다. 각 항목에는 **핵심 설명 → 원리·절충 → 코드·실행 근거 → 변경 시 영향 → 이해 확인/QNA 연결**을 둔다. 관련 없는 세부 항목은 이유와 함께 제외하고, 같은 코드를 여러 항목에서 길게 반복하지 않는다.

| 관점 | 설명해야 할 내용 | 조건 변화의 예 |
|---|---|---|
| 선택 | 문제·목표·제약, 선택한 방법과 실제 대안, 판단 주체, 포기한 이점 | 시간이 절반이거나 정확도 요구가 달라지면? |
| 흐름 | 실제 입력·변환·처리·검증·저장/출력·조회와 상태 소유자 | 요청이 겹치거나 원본 형식이 바뀌면? |
| 검증 | 원본 기반 독립 검증, 신뢰하지 않는 값, 위반 사례 거부, 증거 범위 | 합계·ID·버전이 조작된 출력이 들어오면? |
| 실패 | 시간·크기 한도, 빈 결과·오류·취소·늦은 응답·오래된 데이터, 화면 상태 | 계산 중 원본이 바뀌거나 제한 시간에 도달하면? |
| 품질 | 기준 방법·기대 결과를 검산할 수 있는 작은 사례·조건 변화 결과, 비용과 품질, 증명 유무와 적용 범위 | 입력 규모·용량·가중치를 바꾸면? |
| AI 협업 | 실제 제안의 수용·수정·기각, 사람과 AI의 역할, 실제 전후 차이 | 검토 의견이 명세·관측과 충돌하면? |

설명에는 실제 결정 주체와 근거를 표시한다. 사용자가 아직 답하지 않았다면 “사용자는 이해했다/선택했다”라고 쓰지 않는다. 개인적 소감이나 실제 수행 경험을 대신 지어내지 않는다.

## 3. 근거와 재현 방법

핵심 주장 옆에 요구·결정·실행 기록과 코드 링크를 둔다. 코드 링크는 경로와 함수·라우트·현재 줄 위치 등 다시 찾을 단서를 함께 적는다. 실제 실행에 필요한 명령 또는 UI 순서, 입력 위치, 관련 환경, 확인할 결과를 제공한다. 비밀값 자체는 문서에 복사하지 않는다.

유효성, 경험적 품질, 최적성·정확성 증명을 따로 적는다. 작은 사례의 정확한 해, 알고리즘의 이론적 성질, 특정 코드·입력에서의 실행 결과를 섞지 않는다. 증명이 없다면 없다고 쓰고 어떤 검증으로 대신 위험을 줄였는지 설명한다. 검사하지 않은 범위와 시간 제한 결과의 한계도 드러낸다.

실제 AI 협업 기록은 WORKLOG 또는 문서 매핑된 AI_COLLAB에 연결한다. 수정 전 증거가 없으면 전후 개선 수치를 만들지 않는다. 사용자의 직접 확인 여부는 실제 QNA 답변에서 확인한다.

## 4. 이해 확인은 QNA에서 한다

인수인계에 필요한 핵심 선택·흐름·검증 범위에 대한 질문부터 QNA에 추가한다. 모든 항목을 한 번에 답하게 하거나 문서의 표현을 그대로 쓰게 하지 않는다. 사용자가 이미 충분히 설명한 내용은 반복 확인하지 않는다.

좋은 질문은 사용자가 자기 말로 이유를 설명하거나 작은 조건 변화의 결과를 예측하게 한다. 예를 들어 실제 코드의 특정 지점을 가리켜 “이 입력이 바뀌면 어떤 결과와 상태가 나오는지, 그 이유가 무엇인지”를 묻는다. 질문은 프로젝트 상황에 맞춰 작성하고 관련 근거를 HANDOFF의 해당 항목에 연결한다.

절차:

1. QNA에 질문 ID, 관련 항목·코드·근거, 질문, 사용자 답변란을 둔다. 문서의 설명을 사용자의 답변란에 미리 쓰지 않는다.
2. 채팅에서 그래프의 핵심 경로와 선택·분기를 먼저 설명하고, 답이 필요한 파일 링크와 질문 ID를 안내한다. 답변을 기다리는 동안 가능한 정리·재현 검사는 계속한다.
3. 사용자가 편집하면 파일을 다시 읽고 답변 원문을 보존한다. 의도와 이해를 추측해 답변을 대신 채우지 않는다.
4. 코드·근거에 맞는 부분과 오해·누락을 구체적으로 피드백한다. 뜻이 같으면 표현 차이만으로 다시 설명하게 하지 않는다.
5. 중요한 오해는 그래프·설명의 모호함을 먼저 점검하고 짧은 예시와 좁은 후속 질문으로 확인한다. 선호·목적이 달라졌다면 USER_INTENT와 영향받은 요구·SPEC·계획·결정만 재검토한다.

이해 상태는 실제 관찰 범위로 적는다. 예: `선택 이유 설명 확인`, `원본 변경 처리 설명 보완 필요`, `답변 대기`. 단순한 동의나 문서 전달만으로 전체 이해 완료를 선언하지 않는다.

## 5. 마무리와 재개

산출물 준비, 실행 검증, 독립 검토, 사용자 이해 확인 상태를 분리한다. 답변이 없어도 완성한 자료와 재현 방법은 전달하고, `산출물 준비 완료 / 이해 확인 답변 대기`처럼 정확히 기록한다. 미완료 필수 요구가 있으면 산출물 전체를 완료라고 부르지 않는다.

WORKLOG에 마지막 확인 코드/입력 버전, 단계별 상태, 미해결 질문·영향, 다음 행동을 남긴다. 최종 응답은 실제 완성한 내용, 중요한 검증·한계, HANDOFF와 필요한 QNA 링크를 간결히 전달한다. 이후 답변이나 데이터가 오면 영향받는 단계부터 재개하고 기존 승인을 반복해서 요구하지 않는다.
