# 실제 구현을 이해할 수 있는 그래프

G2에서는 설계의 초안으로, G3~G5에서는 실제 동작으로 갱신하고, G6에서는 HANDOFF에 설명과 함께 제공한다. 사용자가 이유·데이터·상태·검증·한계를 따라갈 수 있어야 한다. 단순한 `분석 → 구현 → 테스트 → 완료` 그림은 이 목적을 충족하지 않는다. [CHECKLIST](checklist-and-gates.md)의 G6 항목은 메인이 단계별로 확인하되 그림 첫 읽기에는 공개하지 않는다.

## 1. 작업 현황과 제품 동작을 분리한다

- **작업 현황:** SPEC 계획의 작업 ID, 선행·병렬·통합 관계, 담당, 완료·검증 대기·보류·미완료 상태와 근거를 WORKLOG에 표시한다. HANDOFF에는 최신 요약 그림을 넣거나 같은 문서의 명확한 위치로 연결한다.
- **제품 설명:** 실제 기능이 어떤 선택과 코드로 구현됐고 무엇이 검증되었는지 아래 관점으로 그린다. 작업 완료율이나 에이전트 목록으로 대신하지 않는다.

## 2. 질문에 답할 수 있는 작은 그림으로 나눈다

그림 수는 고정하지 않는다. 단순한 경우 관점을 합치되 아래 여섯 관점의 적용 여부와 위치를 표시한다. 큰 그림 한 장에 모든 화살표를 겹치지 않는다. 그림마다 제목, 한 문장 설명, 범례, 근거표를 가까이 둔다.

| 관점 | 그래프에 담을 내용 | 독자가 설명할 수 있어야 하는 것 |
|---|---|---|
| 선택과 절충 | 목표·제약 → 실제 대안 → 채택/제외 이유 → 얻은 점·포기한 점; 판단 주체·결정 ID | 왜 이 방법인가, 어떤 조건에서 다른 방법이 나은가 |
| 요청·데이터 흐름 | 실제 역할·화면/CLI/API → 처리 컴포넌트 → 계산 → 진행 표시 → 검증 → 반영·저장 → 조회; 중요 값·단위·ID/버전·상태 소유자 | 한 요청의 값이 어디서 생기고 바뀌며 어떤 단계가 실제 끝났는가 |
| 신뢰 경계 | 기준이 되는 원본·규칙 → 검증기, 생성기 → 검증 전에는 신뢰하지 않는 출력 → 검증기, 통과/거부 경로 | 어떤 주장을 믿지 않고 무엇을 독립 계산하는가, 유효성 확인이 품질·최적성 보장은 아닌 이유 |
| 실패·변경 | 정상 상태와 실제 오류·실행 한도·지연·취소·원본 변경의 전이 조건, 집행 코드 | 각 사건의 **계산/결과 처리·사용자 표시·저장/기존 결과 상태**는 무엇인가 |
| 품질·한계 | 주장 → 비교/검산/조건 변화 실험 → 실제 관측값 → 적용 범위·미확인·추가 검증 | AI 설명 외에 어떤 근거가 있는가, 입력·가중치 변경이 무엇에 영향을 주는가 |
| 실제 리뷰·협업 | 실제 발견 주체·방법 → 재현 → 제안 → 수용/수정/기각 판단 → 코드 변경 → 재검사 → 남은 한계 | 누가 무엇을 왜 바꿨고 어떤 실행으로 확인했는가 |

없는 기능·상태·비교·실패·기각 사례를 그림을 채우기 위해 만들지 않는다. 진행률이 없으면 없다고 설명한다. 있다면 건수·단계·시간 등 실제 산정 기준을 밝히고, 계산 완료·검증 완료·저장 완료를 구분한다. 검토에서 결함이 발견되지 않았다면 실제 확인·수용 근거를 그리며 가짜 결함을 만들지 않는다.

품질 비교의 입력·제약·자원 조건과 수치를 인접 표에 둔다. 다른 가중치의 총점을 그대로 개선율로 비교하지 않는다. 증명이 없으면 `최적성 미확인`처럼 분명히 표시한다. 미구현·미실행 분기를 정확하게 설명할 수는 있지만 제품 검증 완료로 판정하지 않는다.

## 3. 코드와 근거에 닿는 표기를 쓴다

각 그림에 짧은 ID를 붙인다. 예: `D` 선택, `F` 흐름, `V` 검증, `S` 상태, `E` 실험, `C` 협업. 표와 질문에서 노드 ID를 참조한다면 **렌더링된 노드의 라벨에도 그 ID가 보여야 한다.** Mermaid 코드 내부의 식별자만으로는 독자가 그림과 표를 연결하기 어렵다. 그림 안에는 실제 역할·컴포넌트 이름과 핵심 조건을 적고, 길어지는 코드·로그 정보는 인접 표로 옮긴다.

| 그림·노드/연결 ID | 의미·주요 전달 값/조건 | 코드 위치·명세/결정 | 실제 검사·관측 결과 | 상태·한계 |
|---|---|---|---|---|
| 실제 ID | 필드·단위·버전 또는 분기 조건 | 파일·함수와 명세 ID | 근거 ID·입력/코드 버전·실행 위치 | 설계/구현/검증/미확인 |

데이터 전달, 제어·상태 전이, 판단 근거의 화살표 의미를 구분하고 범례에 적는다. 조건부 실패는 화살표에 발동 조건을 쓰고 정상 경로도 표시하거나 연결 위치를 알려, 모든 요청이 실패하는 것처럼 보이지 않게 한다. 색상만으로 상태를 구별하지 않는다. 서로 다른 그림에서 같은 컴포넌트·상태·버전에 다른 이름을 붙이지 않는다. 그림과 인접 설명만으로 핵심 설명이 성립해야 하며, 링크는 세부 재현·확인에 사용한다.

실행 주장은 마지막 코드·입력 버전에 맞는 근거로 연결한다. 문서가 바뀐 뒤 오래된 그림을 그대로 두지 않는다. 사용자 판단과 에이전트 판단은 출처에 따라 구별한다.

## 4. 읽을 수 있는 형태로 제공한다

Markdown에는 Mermaid 흐름도·시퀀스도·상태도를 우선 사용한다. 세부 경로가 길면 정상 경로와 예외 분기를 나누고, 실제 요청 하나의 입력부터 최종 상태까지 그림을 따라 설명한다. 측정값 차트는 실제 값이 있을 때만 추가한다.

가능한 렌더러에서 구문·잘린 글자·겹친 화살표·너무 작은 글씨를 확인한다. 긴 라벨은 짧게 쓰고 의미 단위로 줄을 나눠 단어가 한 글자씩 끊기지 않게 한다. 렌더러가 없는 환경에서는 그 한계를 기록하고 동일 내용을 읽을 수 있는 텍스트 흐름과 표를 제공한다. 그림 코드를 작성했다는 이유만으로 렌더링·가독성 검증을 완료했다고 하지 않는다. 외부 게시 없이 허용된 작업 경로에서 확인한다.

## 5. 새 맥락 독자가 먼저 읽고 사실을 대조한다

G5 제품 검증만으로 G6에서 새로 만든 설명이 검증되었다고 가정하지 않는다. [에이전트 운영](agents-and-resume.md)의 새 맥락 조건을 만족하고 그림 작성에 참여하지 않은 검토자가 아래 두 단계를 수행한다. 제품 전체 감사를 반복할 필요는 없다.

1. **읽기 검토:** 그림과 인접 범례·표·요약, 프로젝트에 맞춘 여섯 관점 질문만 제공한다. 작성자의 해설·모범 답·부모 결론은 주지 않는다. 검토자가 자기 말로 답하고 정상 요청 하나와 적용되는 실패/변경 하나의 결과·표시·저장 상태를 추적하게 한다. 답할 수 없는 부분·해석 갈림·지목한 근거 ID를 먼저 고유 보고서에 저장한다. 이 단계에서는 링크 너머 코드·로그를 열지 않는다.
2. **사실 대조:** 첫 보고를 보존한 뒤 원자료·확인된 요구·SPEC·현재 코드·실행 기록·CHECKLIST를 공개한다. 해석과 실제 동작의 일치, 누락된 중요한 분기, 근거 버전, 과장된 품질·완료 주장을 대조한다. 필요한 검사는 허용된 범위에서 실행하고 미실행은 표시한다.

**통과 조건:** 적용되는 각 관점에 구체적인 답과 근거 위치가 있고, 중요한 동작·상태·주장에 사실 오류가 없으며, 작성자의 구두 보충 없이 핵심 경로를 추적할 수 있다. 빠진 중요 근거, 잘못된 상태 전이, 설명 없이 표제어만 있는 그림은 보완 대상이다. 메인은 지적을 실제 확인해 수정/근거 있는 기각/미해결을 기록하고 영향받은 연결·질문만 다시 검토한다.

**수정 뒤의 읽기 독립성:** 사실 대조로 코드를 알게 된 검토자는 그림의 설명 부족을 코드 지식으로 메울 수 있다. 의미·경로·핵심 설명을 바꾼 경우, 영향받은 그림·인접 설명·질문만 **새 맥락의 다른 독자**에게 제공해 첫 읽기를 다시 수행한다. 이전 검토자는 변경의 사실 대조를 계속할 수 있다. 의미가 같은 오탈자·줄바꿈·선 배치 수정은 기존 검토자의 시각 재확인으로 충분하며 전체 검토를 반복하지 않는다. 각 결과를 해당 G6 체크 항목의 근거에 연결한다.

HANDOFF에 `관점 → 그림·노드 → 설명 가능한 내용 → 코드/근거 → 독립 검토 결과` 표를 둔다. 읽기 검토 통과, 사실 대조 통과, 렌더링 확인, 제품 검증 상태는 분리해 남긴다. 도구가 없거나 검토가 불가능하면 해당 상태를 미완료로 둔다.

## 6. 사용자의 이해로 이어간다

메인은 검토한 그래프를 따라 핵심 경로와 중요한 선택·실패 분기를 설명한다. QNA에는 특정 노드의 이유, 조건 하나가 바뀔 때의 결과, 보장하지 않는 범위를 묻는 질문을 둔다. 답변에서 오해가 드러나면 사용자의 탓으로 돌리지 말고 모호한 그림·설명을 먼저 보완한다. 에이전트의 읽기 검토 통과와 실제 사용자의 이해 확인은 별개다. 답변이 없으면 준비된 자료는 전달하되 이해 확인은 대기로 유지한다.
