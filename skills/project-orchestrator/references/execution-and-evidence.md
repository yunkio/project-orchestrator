# 실행과 검증 근거

G2에서 계획할 때 읽고 G3–G5에서 실제 결과로 갱신한다. 목적은 요구 충족과 판단의 근거를 남기는 것이다. 특정 기술 사용, 실험 수, 문서 분량을 성과로 삼지 않는다. 기록은 WORKLOG의 결정·실행 흐름·검증·협업 구역에 통합한다.

## 1. 구현 전에 정할 것

USER_INTENT와 REQUIREMENTS를 다시 읽고 G2의 SPEC 명세·계획으로 연결한다. 구현·테스트는 해당 버전의 명세 절·작업 ID·통과 조건을 기준으로 한다. 각 핵심 요구를 `입력/상황 → 기대 동작 → 금지 결과 → 확인 방법`으로 표현한다. 화면 존재, 실제 계산, 저장, 결과 조회를 구분한다. 기존 자료에서 확정된 조건을 다시 선택하게 하지 않는다.

중요한 설계 선택은 아래 항목으로 짧게 기록한다. 현실적인 대안이 하나뿐이면 없는 대안을 꾸미지 않는다.

| 결정 | 남길 내용 |
|---|---|
| 목적·근거 | 관련 요구/의도 ID, 원자료 위치, 성공 기준 |
| 대안·절충 | 채택안과 실제 대안, 시간·품질·복잡성·운영 비용, 포기한 이점 |
| 판단 | 선택 이유, 사용자 직접 결정인지 에이전트 판단인지, QNA 또는 기록 링크 |
| 유효 범위 | 가정, 입력 규모·환경, 선택을 다시 검토할 조건 |

사용자 가치·업무 우선순위·허용 위험 등 미확정 판단은 QNA에서 확인한다. 이미 위임받은 구현 선택은 근거를 남기고 진행한다. AI의 합리적인 추정도 사용자 발언이나 승인으로 바꾸지 않는다.

실행 가능한 가장 작은 전체 경로부터 계획한다. 구현·검증·수정·설명에 사용할 시간을 나누고, 선택 기능보다 필수 동작과 실패 방지를 우선한다. 시간 부족으로 못 끝낸 필수 요구를 선택 기능으로 바꾸지 않는다.

## 2. 실제 코드에 연결한 실행 흐름

WORKLOG에 입력부터 최종 조회까지 하나의 흐름도를 유지한다. 초기에는 `설계안`으로 표시하고, 구현 뒤 노드와 연결선을 실제 코드에 맞춘다. 아래는 필요한 단계만 고르는 골격이며 없는 API·DB·큐를 추가하라는 뜻이 아니다.

```text
사용자 입력 → 입력 검증 → 권위 있는 원본/버전 확보 → 처리 요청
  → 결과 생성 → 원본·규칙으로 검증 → 현재 요청/버전 확인
  → 결과 반영·저장(해당 시) → 화면 또는 결과 조회
```

- 노드마다 파일·함수·라우트 등 확인 가능한 코드 위치를 연결한다. 연결선에는 데이터 형태, 단위, ID, 요청/원본 버전 등 중요한 전달 값을 표시한다.
- 외부 입력의 출처, 읽는 시점, 기본값, 변환, 상태 소유자, 저장·캐시 위치를 설명한다. 메모리만 사용하면 그대로 쓴다.
- 실제 제공 인터페이스에서 한 요청을 따라 입력→처리→검증→출력→조회가 연결되는지 확인한다. 웹은 화면, CLI는 명령과 저장 결과, API는 요청·응답을 사용한다. 개별 함수 검사나 스크린샷만으로 전체 경로가 작동한다고 판단하지 않는다.
- 데이터 그래프·최적화 모델이 있다면 실제 필드가 노드·간선·변수·제약·목적함수로 어떻게 바뀌는지 별도로 설명한다. 수학적 모델과 구현의 변환 코드를 연결하고 단위·경계·누락을 검사한다.

흐름도는 설명용 장식이 아니다. 실제 코드에 대응하지 않는 노드를 지우거나 미구현으로 표시하고, 코드를 바꾼 뒤 영향받은 설명을 갱신한다. 최종 HANDOFF에는 [그래프 설명·검증 절차](graph-handoff.md)에 따라 선택·검증 경계·실패·품질·실제 협업 근거까지 연결한다.

## 3. 실행 한도·실패·데이터 변경

작업 특성에 맞는 실제 한도와 실패 동작을 정한다. 단순한 동기 작업에 분산 실행 구조를 도입할 필요는 없다.

| 조건 | 구현·확인할 내용 |
|---|---|
| 시간·크기·비용 한도 | 어디에서 제한을 집행하는지, 초과 시 계산이 멈추는지, 결과가 어떻게 표시되는지 |
| 잘못된 입력·원본 불일치 | 어떤 규칙으로 거부하는지, 사용자가 수정할 정보가 보이는지 |
| 해 없음·빈 결과 | 정상적인 빈 결과와 계산 실패를 구분하는지 |
| 시간 초과·부분 결과 | 검증된 후보만 표시하는지, 탐색 완료·최적 해로 오인시키지 않는지 |
| 외부 호출 실패 | 오류 표시, 필요한 경우에만 상한 있는 재시도, 중복 변경 방지 |
| 취소·늦은 응답 | 이전 요청의 결과가 최신 요청을 덮어쓰지 않는지 |
| 원본 변경·캐시 만료 | 결과가 어떤 원본 버전에 속하는지, 폐기·재검증·재계산 정책이 실제 적용되는지 |

사용자에게 실제로 가능한 `대기`, `처리 중`, `완료`, `부분 결과`, `해 없음`, `입력/검증 오류`, `시간 초과/취소`, `갱신 필요` 상태를 명확히 보여준다. 모든 상태를 강제로 만들지는 않는다. 오래된 결과를 계속 보여줄 때에는 그 상태와 기준 시점을 표시한다. UI에 적힌 제한과 실행 코드의 제한이 일치해야 한다.

시간 내 후보를 찾지 못한 상태와 가능한 해가 없음을 확인한 상태를 구분한다. 탐색 제한과 요청 응답 제한도 같다고 가정하지 않는다. 진행률은 실제 처리 단계·건수·시간 기준을 밝히고, 시간 경과 비율을 품질이나 최적성의 달성 비율로 표시하지 않는다. 계산 완료·검증 통과·저장 완료는 각각 실제로 끝난 시점에 반영한다.

비동기 경로에는 순서를 바꾼 응답과 계산 중 원본 변경을 주입해 확인한다. 정책이 문서에만 있고 실행 중 적용되지 않으면 미구현이다.

## 4. 생성기와 분리한 출력 검증

생성기의 성공 플래그·합계·점수·제약 충족 주장을 그대로 믿지 않는다. 독립 검증은 권위 있는 원본과 명세의 규칙에서 출력의 유효성을 다시 판단한다. 출력 ID로 원본의 비용·속성·관계를 읽고 필요한 합계와 제약을 재계산한다.

- 공통 파싱·스키마를 재사용할 수 있으나 생성기 내부 상태나 동일한 계산 함수를 그대로 믿는 것만으로 독립성이 생기지 않는다. 핵심 조건은 별도 경로로 확인한다.
- 문제에 맞게 알려진 ID, 중복·누락, 범위·단위, 수량·용량, 순서·관계, 역할·권한, 허용 오차, 원본 버전을 검사한다. 적용하지 않는 조건을 억지로 추가하지 않는다.
- 정상 결과와 함께 위반 결과를 직접 주입한다. 예: 조작된 합계, 미등록 ID, 중복 선택, 제한 초과, 오래된 버전. 검증기가 실제로 거부하거나 신뢰할 수 있는 값으로 재계산하는지 확인한다.
- 계산·생성 문제가 아닌 작업은 원본 상태와 명세에서 기대 결과를 독립적으로 만들고 실제 동작과 대조한다. 구현을 그대로 따라 쓴 기대값만으로 검증하지 않는다.
- 검증 실패를 성공 화면으로 통과시키지 않는다. 현재 입력과 다른 버전의 유효 결과도 현재 요청의 성공 결과는 아니다.

### 주장 수준을 구분한다

| 수준 | 필요한 근거 | 주장 범위의 제한 |
|---|---|---|
| 유효성·실행 가능성 | 원본에 대한 제약 검사, 위반 사례 거부 | 결과가 좋거나 최적이라는 뜻은 아님 |
| 경험적 품질 | 명시한 입력·조건에서 기준 방법과 비교한 관측 | 모든 입력에서 더 좋다는 뜻은 아님 |
| 최적성·정확성 증명 | 가정이 맞는 증명, 완전 탐색, 검증 가능한 인증서·하한/상한 | 증명이 다루는 모델·입력·조건에만 적용 |

작은 사례의 정확한 해와 일치하면 그 사례에서 확인한 사실로 쓴다. 알고리즘의 이론적 성질, 모델의 타당성, 코드의 정확성, 특정 실행의 종료 상태를 구분한다. 솔버의 `optimal` 출력만으로 이 네 가지가 모두 입증되지는 않는다. 시간 제한에서 얻은 후보는 확인된 상한/하한·gap이 있을 때 그 의미를 설명하고, 없으면 최적성 미확인으로 표시한다.

## 5. 프로젝트에 맞는 품질 실험

기능·필수 제약과 실패 동작을 먼저 검증한다. 비교·최적화·예측 등 품질 차이가 중요한 프로젝트라면 다음 실험 중 필요한 것을 수행한다. 적용하지 않는 항목은 짧게 이유를 기록한다. 단순한 화면 수정에 완전 탐색이나 통계 실험을 붙이지 않는다.

| 실험 | 실행 방법 | 해석 |
|---|---|---|
| 기준 방법 | 단순하고 실행 가능한 방법과 동일 입력·목표·제약·자원 조건에서 비교 | 복잡한 방법의 추가 가치가 있는지 확인 |
| 기대 결과를 검산할 수 있는 작은 사례 | 작은 입력을 손으로 검산하거나 독립 완전 탐색으로 해결 | 모델·목적함수·변환·생성기·검증기의 오류 탐지 |
| 조건 변화 | 중요한 규모·용량·가중치·오차·시간 한도를 바꿈 | 결과·지연·실패의 변화, 임계점과 민감도 확인 |

관련 환경, 입력/코드 버전, seed, 종료 조건을 남긴다. 측정하지 않은 속도·품질 향상을 쓰지 않는다. 한 번의 실행으로 평균·안정성을 주장하지 않는다. 기준 방법보다 못하면 숨기지 말고 원인과 선택에 미친 영향을 적는다. 확인한 조건 밖의 보장은 별도 근거가 없으면 하지 않는다.

가중치를 바꾸면 총점의 의미도 바뀐다. 서로 다른 가중치의 총점을 그대로 개선율로 비교하지 말고 원래 단위의 개별 지표도 함께 확인한다. 난수를 쓰면 재현 조건과 여러 실행의 차이를 구분하며, 다른 조건의 실행에 대해 탐색 시간이 길수록 반드시 좋다고 단정하지 않는다.

새 테스트는 의미 있는 동작·불변 조건을 확인할 때 추가한다. 테스트 수를 채우거나 구현을 그대로 복사한 검사를 만들지 않는다. 기존 검사가 충분하면 재사용한다. 관련 검사가 통과한 뒤에는 새 변경·실패·남은 우려가 없으면 반복 측정 대신 마무리로 진행한다.

## 6. 실행과 AI 협업의 실제 기록

핵심 주장마다 WORKLOG에 아래 연결을 남긴다. 상세 로그가 길면 원본 파일을 링크하고 핵심 출력만 요약한다.

| 주장/요구 | 입력·환경·코드 위치/버전 | 명령 또는 UI 동작 | 실제 결과 | 판정·한계 |
|---|---|---|---|---|
| 확인 대상 | 재현에 필요한 정보 | 실제 실행한 내용 | 종료 코드·출력·관찰값 | 통과/실패/일부 확인/미실행 및 범위 |

실행 계획과 실행 결과를 구분한다. 에이전트가 보고한 결과는 출처를 적고, 메인이 직접 확인한 결과와 구분한다. 사용자가 직접 실행·확인했다는 주장은 QNA 답변 등 실제 근거가 있을 때만 쓴다. 마지막 수정 이후 오래된 검사 결과는 현재 코드의 통과 근거로 쓰지 않는다.

중요한 AI 제안·오류·검토 지적만 협업 기록에 남긴다. 기존 AI_COLLAB 문서가 같은 역할을 한다면 WORKLOG 문서 매핑에 연결하고 중복 작성하지 않는다.

| 실제 제안/지적·출처 | 판단 주체·수용/수정/기각/보류 이유 | 실제 변경 | 변경 전후 근거 |
|---|---|---|---|
| 대화·검토의 핵심 | 사용자 답변 또는 에이전트 결정 링크 | 파일·함수, 또는 변경 없음 | 실행 명령·동작과 실제 결과, 없으면 미확인 |

없는 실패나 기각 사례, 가상 대화, 실행하지 않은 전후 결과를 만들지 않는다. 협업 사례 수를 채우기 위해 불필요한 제안을 유도하지 않는다. 변경 전 증거가 없으면 없다고 쓰고, 사용자 작업을 되돌려 과거를 재현하지 않는다. 결함을 실제 재현했다면 `동일 입력의 실패 → 원인 → 최소 수정 → 동일 실패와 관련 정상 사례 재검사`를 연결한다.

## 7. 통합·최종 검토로 넘기기

[요구 감사](requirements-and-audit.md)와 [에이전트 운영](agents-and-resume.md)의 독립성·수정 소유권을 따른다. 새 맥락 감사자에게 원하는 결론을 주입하지 않는다. 통합 후에는 개별 모듈뿐 아니라 실제 사용자 경로와 공유 데이터 계약을 다시 확인한다.

지적의 위치·재현 조건·영향을 확인하고 수정·기각·미해결 및 이유를 WORKLOG에 남긴다. 변경된 요구·코드·검사·흐름도만 갱신한다. 구현 완료, 검증 완료, 사용자 이해 확인을 별개로 표시한다. 필수 요구의 미충족과 남은 위험을 HANDOFF 및 최종 보고에 이어 전달한다.
